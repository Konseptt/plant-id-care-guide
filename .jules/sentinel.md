## 2026-06-24 - [Broken Double Submit Cookie CSRF Validation]
**Vulnerability:** The CSRF validation logic (`validateCsrfToken` in `server.js`) was broken. It generated a token and set it in a cookie, but only verified if the token existed in the server's state, rather than verifying if the client explicitly submitted the token via an alternate channel (like a request parameter or header) alongside the cookie. Furthermore, the `crypto.timingSafeEqual` check was effectively a no-op because it compared the cookie token to itself (`Buffer.from(token, 'hex')` vs `Buffer.from(token, 'hex')`).
**Learning:** A proper Double Submit Cookie or Synchronizer Token Pattern requires two distinct inputs: one from the cookie and one from the request body, header, or query parameters. Comparing a value to itself is a common implementation flaw when attempting to build secure comparison logic without fully understanding the underlying pattern.
**Prevention:** Always verify that cryptographic comparisons use two distinct variables sourced from different parts of the request (e.g., cookie vs. query parameter). When implementing CSRF protections, ensure the token is both sent in a cookie and returned via a non-cookie mechanism (like a custom header or query param) and that the server explicitly compares these two values.
